# プレDD レポート（10 章）

## 何を変えたか

**静的データは自社 DB に事前投入し、動的データと LLM だけ都度 API を叩く。**

以前の 4 段は、統計から特徴を抽出し（1）、問いを立てて Web で調べ（2）、需要
形成の筋道を組み立て（3）、レポートに書き直す（4）——という構成でした。**仮説を
立てて検証する筋書きが、そのまま本文になっていました。** 問いと仮説の一覧が
前に出て、読み手が知りたい「この商圏はどうなのか」がどこにも無い文書です。

いまは 2 段です。

| 段 | 何をするか | API |
|---|---|---|
| 1. 事実の確定 | 人口メッシュ・医院の位置と開設年・駅・地価・都市計画を数え直す | **叩かない** |
| 2. レポート執筆 | 確定した事実を読んで、散文を書く | 1 回 |

費用は 1 本あたり最悪 $0.49 → **$0.06**。Web 検索は 0 回です。

## なぜ事実の層に LLM を入れないか

費用の話だけではありません。**同じ地点なら何度実行しても同じ数字が出る**ように
するためです。DD の文書で「先週と今週で結論が違う」が起きると、その文書ごと
信用されなくなります。

事実は `kaigyou_core/dd.py` が組み立てます。LLM が書くのは 4 つだけです。

    Executive Summary       結論から
    章ごとの読みどころ       その章の事実が何を意味するか
    成長余地の仮説           但し書きつき
    総合評価                 開業する人と、買う人に分けて

**数字は作らせません。** 本文の数値を事実の束と照合し、束に無い数字があれば
レポートは保存されません（`verify_dd_report`）。年号と 1 桁は見逃します——拾うと
ほぼ全文が引っかかって使い物になりません。

## 章立て

設定（`config/<業態>/dd.yaml` の `chapters`）が決めます。

1. Executive Summary — LLM
2. 商圏分析 — 面積・リング別人口・メッシュの偏り
3. 競合分析 — 半径別件数・近さの階段・開設年・各院の中身
4. 立地分析 — 駅との関係・用途地域・地価
5. 人口・需要分析 — 年齢構成・昼間人口
6. 将来性 — 将来推計（有無を先頭に）・競合の入れ替わり
7. リスク — **該当したものだけ**
8. 成長余地・KSF — 周囲と比べた位置・空いている領域・KSF の問い
9. 追加DDで確認すべき事項 — 原理的に取れないものと、今回取れなかったもの
10. 総合評価 — 開業する人と、買う人に分けて

## 2 通りの読み手

    これから開業する人   …… ここで開業して患者が来るか
    既存医院を買う人     …… 承継後も患者が残るか、のれん代の前提は何か

**同じ事実を、違う問いで読みます。** だから総合評価は分けて書きます。

## リスクの線引き

`dd.yaml` の `risks` に、しきい値と文言を置いています。**数え方はコードです**
——設定に数え方まで書けるようにすると、設定ファイルが小さな言語になって、
書き間違いが黙って無視されます。

実装のない判定を指したリスクは、起動時に `UnknownRiskCheck` で落ちます。黙って
無視すると、そのリスクは永久に該当しません。引っかからないのか判定していない
のかが区別できなくなります。

該当したものだけを出します。**該当しなかった項目を並べると、調べた量が多く
見えるだけです。**

## 競合の中身は、別の分析から借りる

第 3 章の「各医院の中身」は、同じ地点で「周辺の競合を分析する」を走らせて
いれば自動で埋まります。走らせていなければ、そう書きます——件数と距離は施設
データベースから出ますが、各院が何を掲げているかは Web を見ないと分かりません。

これが「静的／動的」の切れ目です。件数と位置は静的（DB）、各院の訴求は動的
（都度 API）。

## 旧・4 段は残してあります

`analysis_kind = research` として残しました。問いと仮説の筋書きを見たいときは
そちらを走らせられます。既定（`area`）から外しただけです。
