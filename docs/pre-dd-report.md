# プレDD レポート（10 章）

## 何を変えたか

**静的データは自社 DB に事前投入し、動的データと LLM だけ都度 API を叩く。**

以前の 4 段は、統計から特徴を抽出し（1）、問いを立てて Web で調べ（2）、需要
形成の筋道を組み立て（3）、レポートに書き直す（4）——という構成でした。**仮説を
立てて検証する筋書きが、そのまま本文になっていました。** 問いと仮説の一覧が
前に出て、読み手が知りたい「この商圏はどうなのか」がどこにも無い文書です。

いまは 2 段です。

| 段 | 何をするか | API |
|---|---|---|
| 1. 事実の確定 | 人口メッシュ・医院の位置と開設年・駅・地価・都市計画を数え直す | **叩かない** |
| 2. レポート執筆 | 確定した事実を読んで、散文を書く | 1 回 |

費用は 1 本あたり最悪 $0.49 → **$0.06**。Web 検索は 0 回です。

## なぜ事実の層に LLM を入れないか

費用の話だけではありません。**同じ地点なら何度実行しても同じ数字が出る**ように
するためです。DD の文書で「先週と今週で結論が違う」が起きると、その文書ごと
信用されなくなります。

事実は `kaigyou_core/dd.py` が組み立てます。LLM が書くのは 4 つだけです。

    Executive Summary       結論から
    章ごとの読みどころ       その章の事実が何を意味するか
    成長余地の仮説           但し書きつき
    総合評価                 開業する人と、買う人に分けて

**数字は作らせません。** 本文の数値を事実の束と照合し、束に無い数字があれば
レポートは保存されません（`verify_dd_report`）。年号と 1 桁は見逃します——拾うと
ほぼ全文が引っかかって使い物になりません。

## 章立て

設定（`config/<業態>/dd.yaml` の `chapters`）が決めます。

1. Executive Summary — LLM
2. 商圏分析 — 面積・リング別人口・メッシュの偏り
3. 競合分析 — 半径別件数・近さの階段・開設年・各院の中身
4. 立地分析 — 駅との関係・用途地域・地価
5. 人口・需要分析 — 年齢構成・昼間人口
6. 将来性 — 将来推計（有無を先頭に）・競合の入れ替わり
7. リスク — **該当したものだけ**
8. 成長余地・KSF — 周囲と比べた位置・空いている領域・KSF の問い
9. 追加DDで確認すべき事項 — 原理的に取れないものと、今回取れなかったもの
10. 総合評価 — 開業する人と、買う人に分けて

## 2 通りの読み手

    これから開業する人   …… ここで開業して患者が来るか
    既存医院を買う人     …… 承継後も患者が残るか、のれん代の前提は何か

**同じ事実を、違う問いで読みます。** だから総合評価は分けて書きます。

## リスクの線引き

`dd.yaml` の `risks` に、しきい値と文言を置いています。**数え方はコードです**
——設定に数え方まで書けるようにすると、設定ファイルが小さな言語になって、
書き間違いが黙って無視されます。

実装のない判定を指したリスクは、起動時に `UnknownRiskCheck` で落ちます。黙って
無視すると、そのリスクは永久に該当しません。引っかからないのか判定していない
のかが区別できなくなります。

該当したものだけを出します。**該当しなかった項目を並べると、調べた量が多く
見えるだけです。**

## 競合の中身は、別の分析から借りる

第 3 章の「各医院の中身」は、同じ地点で「周辺の競合を分析する」を走らせて
いれば自動で埋まります。走らせていなければ、そう書きます——件数と距離は施設
データベースから出ますが、各院が何を掲げているかは Web を見ないと分かりません。

これが「静的／動的」の切れ目です。件数と位置は静的（DB）、各院の訴求は動的
（都度 API）。

## 第II部：開業提言

「分析を開始する」を押すと、**2 部構成の文書**が 1 本できます。

| | 何を書いてあるか | 推論 | 外部検索 |
|---|---|---|---|
| 第I部 商圏プレDD | この商圏が**どうなっているか**（10章） | しない | なし |
| 第II部 開業提言 | ここで開業するなら**どうするか**（10章） | する | あり |

**分けてあるのは、混ぜると第I部が信用を失うから**です。事実の文書に戦略提言が
混ざると、読み手はどこまでが確定でどこからが提案なのか分からなくなります。

以前「仮説形成に執着して本文を見失っている」とされたのは、この 2 つが 1 本の
文書になっていたからでした。**推論をやめたのではなく、置き場所を分けました。**

### 第II部の章立て

1 主要患者／2 準主要患者／3 積極的に競争すべきではない患者層／4 第1商圏／
5 第2商圏／6 患者を引き込む理由／7 推奨する医院モデル／8 差別化の方向性／
9 開業上の主要リスク／10 開業前に追加取得すべき情報

### 考える順番

STEP3 のプロンプトが、次の順で考えさせます。

    STEP1 FACT の把握        平均から乖離／組み合わせで意味が変わるデータを抽出
    STEP2 PATTERN の発見     単独の数値ではなく、複数を組み合わせて地域構造を見る
    STEP3 WHY 仮説の生成     因果を断定せず、複数の可能性を並べる
    STEP4 外部コンテクスト   ここで初めて Web。**仮説を検証するために**使う
    STEP5 仮説検証           確認できたこと／できなかったことを印で分ける
    STEP6 患者像の推定       想像で作らず、人口＋年齢＋世帯＋産業＋交通から
    STEP7 開業戦略           上の 10 章へ

外部情報は、**JSON のどの特徴を説明するために必要なのか**を明示させます。
地域紹介（「◯◯市には△△があります」）に使わせません。

    JSON の特徴 → 外部コンテクスト → その特徴が生じている可能性

### 印で、確定と推測を分ける

付録に推論の連鎖を残します。`FACT` `BENCHMARK` `PATTERN` `WHY` `HYPOTHESIS`
`INSIGHT` `IMPLICATION` `ACTION`。**ACTION まで届いていない提言は保存されません**
——示唆で終わるなら、それは提言ではありません。

### 情報不足を機会と読み替えさせない

**この文書でいちばん起きやすい壊れ方です。** 競合の中身を 1 件も見ていないのに
「競合が少ない」と書くと、情報不足がそのまま機会に化けます。コードで弾きます。

- 調べた競合が 0 件のときに「競合が少ない／弱い」と書いていたら保存しない
- 調べていないなら `information_gaps` にそう書かせる（空なら保存しない）
