# 周辺の競合を分析する（3C の Competitor）

開発指示書「地域競合分析AI MVP」の実装メモ。

これまで、Web 検索のリソースは**地域について広く調べる**ことに使っていました。
それをこちらへ振り替えます。地域の統計は既に手元にあり、Web を引かなくても
読めます。**手元に無いのは競合の中身のほうです**——各院が何を掲げ、誰に向け、
いくらで、いつ開いているのか。届出データベースには標榜科目しかなく、
インプラントも審美も訪問診療も、そこには載っていません（東京都で
インプラントの記載は 1% 台）。

---

## 1. 2 つの分析は、続きではありません

画面のボタンは 2 つです。

| ボタン | 何をするか | 段 | 検索 |
|---|---|---|---|
| 周辺一般の分析を開始する | 統計から地域の構造を読む | 4 | PATTERN ごとに 2 回 ≒ 8 回 |
| 周辺の競合を分析する | 1 件ずつ Web で調べて構造化する | 2 | 1 件 2 回 × 上限 12 件 = 24 回 |

**詳細版でも続きでもありません。** 見るものが違うので、同じ実行の中には
入れられません。片方を走らせたあとにもう片方を走らせることはできますが、
それは 2 本のジョブです。

種類は `analysis_jobs.analysis_kind`（マイグレーション 036）に入ります。
段の構成（`jobs.steps_for`）、段の実装（`worker.runners_for`）、プロンプトの
設定（`config/analysis.yaml` の `steps` / `competitor_steps`）が、すべて
これで切り替わります。

**列が無い環境では周辺一般として扱います。** デプロイとマイグレーションの
間には窓があり、そこで落ちると「まだ当てていない」が「壊れている」に
見えます。

---

## 2. Fact → Analysis → Hypothesis を、実装で分ける

指示書 §8 の三層は、そのままモジュールの境目です。

```
Fact        Web / GIS から確認できた事実   comp1_survey.py（LLM + Web検索）
Analysis    集計・比較した結果             kaigyou_core/competition.py（Python）
Hypothesis  そこから考えられる市場機会     comp2_summary.py（LLM、検索なし）
```

**数え上げを LLM にやらせません。** 数えた結果は検算できますが、モデルが
数えたと言った数は検算できません。STEP2 の入力には集計済みの数字が入って
いて、プロンプトは「数えるのは済んでいます」と言います。レポートに出る
件数も、LLM の文ではなくこの集計値です。

距離も同じです。GIS が確定した `distance_m` を、構造化のあとで付け直します
（`_with_distance`）。モデルに書かせると、それらしい数字が返ってきます。

出典も同じです。検索結果に無かった URL を書いた項目は落とします
（`_drop_unverifiable`）。

## 3. 1 件ずつ呼ぶ

12 件を 1 回の呼び出しにまとめません。理由は 2 つあります。

**速さ。** サーバ側の検索ループが 1 本の中で直列に回り、増えていく文脈を
毎回読み直します。STEP2 で実測済みです（4 検索で入力 794,572 トークン・
5 分 36 秒）。調べる中身は医院ごとに独立しているので、分けても答えは
変わりません。変わるのは待ち時間です（`survey.parallel: 4`）。

**文法の大きさ。** 全医院を 1 つの出力に入れると、構造化出力のスキーマが
大きくなりすぎて API が 400 を返します（`The compiled grammar is too large`）。
`Competitor` は 1 件ぶんのスキーマです。テストが上限（5,200 文字）を見張って
います——**走らせてみるまで分からず、しかも失敗するのは検索を全部終えた
あとの構造化のところ**だからです。

**1 件落ちても全部を捨てません。** 12 件のうち 1 件がしくじっただけで、通った
11 件ぶんの検索と時間を捨てるのは割に合いません。落ちたことは `failed` に
残り、レポートに出ます。

## 4. この分析で起きやすい 3 つの誤読

実装のかなりの部分が、この 3 つを防ぐためにあります。

### 「1km 圏に 12 院」

上限で切った 12 件なのか、本当に 12 院しかないのかで、読み方が正反対に
なります。だから `not_surveyed`（切った件数）と `total_in_radius`（半径内の
総数）を持ち回り、**レポートでも画面でも、どの件数よりも先に**出します。
あとに置くと読まれません。

### 「サイトに書いていない」＝「やっていない」

集計は公開情報から確認できたものの数です。**0 件の行を消しません。**
「この地域に訪問歯科を掲げる医院は無い」は、行が無いことでは伝わりません
——調べ落としと区別が付かないからです。0 件の行は薄く出しますが、消しません。

同じ理由で、確認できなかった項目は `not_confirmed` にまとめ、「駐車場：不明」
の行は作りません。**不明を並べると、調べた量が多く見えます。**

### 「競合が少ない」＝「機会がある」

少ない理由が「まだ誰もやっていない」なのか「やってみて成立しなかった」なのか
は、このデータでは区別できません（指示書 §6）。

- 機会仮説には**必ず但し書き**（`caveat`）が付きます。空なら報告書側で
  補います——但し書きを任意にすると書かれない回が出て、書かれなかった回
  だけが断定に見えます。
- ポジショニングマップの空いている区画にも同じ注意を添えます。

## 5. ポジショニングマップ

2 軸 4 区画。**判定困難を無理に置きません。** 置いてしまうと、図の上では他の
点と同じ確かさに見えます。置けなかった医院は、理由とともに図の外に出ます。

軸そのものは業態の設定です。

```yaml
positioning_map:
  x: {label: 診療の支払い, low: 保険診療中心, high: 自費診療中心}
  y: {label: 診療の幅,     low: 一般診療中心, high: 専門診療中心}
  scale: [-2, -1, 0, 1, 2]
```

**区画の呼び方も設定から作ります。** 「自費 × 専門」をコードに書くと、この
関数は歯科でしか読めません。飲食なら「高価格帯 × 専門店」、学習塾なら
「高価格帯 × 受験対応」です。枠（2 軸 4 区画）は業態を問わず同じで、呼び方
だけが業態のものです。テストが、飲食の設定で動かしたときに歯科の語が
1 つも出てこないことを見張っています。

`0` は「どちらとも言えない」で、判定できなかった（`null`）のとは別です。
軸上の点は区画に押し込まず、別に数えます。

## 6. 業態を足すとき

`config/<業態>/competitors.yaml` を 1 枚作るだけです。

```yaml
label: 歯科医院          # 何を競合と呼ぶか。画面・プロンプト・レポートに出ます
survey:
  radius_m: 1000         # 指示書 §1：基本は 1km 圏
  near_radius_m: 500     # 「近い」の線引き
  max_competitors: 12    # 近い順に切る上限
  searches_per_competitor: 2
  parallel: 4
products: [...]          # 4P の Product に使う語彙
segments: [...]          # STP の Segmentation / Targeting
place_attributes: [...]  # 4P の Place（key と label）
positioning_map: {...}   # 2 軸
```

枠（STP と 4P）はスキーマに、語はここに。だから飲食にも小売にも学習塾にも、
コードを触らずに移せます。

## 6.5 時間の上限（実測で直したもの）

最初に動かしたとき、STEP1 は**終わりませんでした。** 画面には

```
0 / 2 ステップ完了 — STEP1 実行中 12分11秒
STEP1 競合の調査    実行中  12分11秒   やり直し 1回
```

とだけ出ていて、止まっているのか進んでいるのか分かりません。原因は 2 つ
重なっていました。

**呼び出しに上限が無かった。** `anthropic.Anthropic()` を素で作っていたので、
SDK の既定（600 秒 × やり直し 2 回）が効きます。**1 回の呼び出しが最大
1,800 秒**かかりえます。関数の上限は 800 秒です。呼び出しが 1 本詰まるだけで
段はまるごと失われ、調べ終えていた医院の結果も一緒に消えます。
`worker.request_timeout_seconds` / `request_max_retries` で明示しました。

**段そのものに区切りが無かった。** 時間の見張りは段と段の間にしかなく
（`tick` の `reserve_seconds`）、**1 つの段が上限を越えるとき**に何もでき
ませんでした。いまは worker が「この呼び出しに残っている秒数」を STEP1 に
渡します（`_残り秒`）。

区切りに当たったときの振る舞いは、こうです。

| 状況 | どうするか |
|---|---|
| 何院か調べ終えている | **そこで切り上げて段を完了**。残りは `out_of_time` に名前で残り、レポートに出ます |
| 1 院も始められなかった | `OutOfTime`。**失敗として記録しません**——やり直し回数を食わせると、いちばん時間のかかる商圏がいちばん試行回数を使えないことになります |
| 始めてしまった 1 院 | 終わらせます。途中で捨てると、その検索の費用だけが残ります |

**8 院調べて「4 院は時間切れ」と書くほうが、12 院ぶんの費用を捨てるより
良い。** 時間切れは上限で切ったのとは理由が違う（上限は方針、時間切れは
事故で、やり直せば結果が変わりうる）ので、レポートでも分けて書きます。

波の数も減らしました（`parallel: 4` → `6`）。12 院を 4 本ずつだと 3 波で、
1 波の長さはその波のいちばん遅い医院で決まります。

## 7. まだやっていないこと（指示書 §7）

Company 分析、最適 STP / 4P の自動提案、5 Forces、自由な Web リサーチ、
長文の自動レポート。MVP には入れません。

いま動くのは

**競合抽出 → Web調査 → STP/4P構造化 → 競合比較 → ポジショニングマップ**

までです。
