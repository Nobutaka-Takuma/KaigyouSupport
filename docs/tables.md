# テーブル設計 — 事前計算で何を貯めるか

「地図上でポイントを示すだけで、その地域の特徴が分かる」ためには、
**専門家が頭の中でやっていた地域比較を、あらかじめ済ませておく**必要があります。
何を貯めれば足りるのかを、実測から決めました。

---

## 1. 実測：どこに時間が消えていたか

銀座4丁目・半径1km・手元の PostgreSQL（1 往復 0.2ms）。

```
build_dataset 全体 127ms / SQL 59 往復

  measures.measure_scope_shape   8 往復  18.0ms   ← 母集団の大きさと弁別力
  provenance.for_tables          8 往復  24.7ms   ← 出典（ほぼ静的）
  measures._scope_statistics     6 往復  31.3ms   ← 母集団の中の位置
  analysis.analyze_point         3 往復  14.7ms   ← 商圏の集計そのもの
```

**母集団の形を測るのに 14 往復・49ms。商圏の集計そのものは 15ms。**

「この地点が何人か」より「周りがどうなっているか」のほうが 3 倍高い。
これが「地図上にデータを表示する GIS」と「周囲と比べてどんな場所かを評価する
GIS」の値段の差です。

そして——**周りは、クリックした地点によって変わりません。** 静岡県内の市街地の
人口分布は、どこをクリックしても同じです。地点ごとに測り直していました。

---

## 2. どちらの形で貯めるか

2 つの案がありました。

### 案 A：メッシュごとに評価を貯める（地域特徴ベクトル）

```
mesh_positioning(mesh_id, profile, radius_m, 各指標の percentile, 軸の点 …)
```

**採りませんでした。** 利用者は任意の座標をクリックします。その商圏はどの
メッシュの商圏とも一致しません。メッシュごとに評価を貯めても、答えられるのは
**「いちばん近いメッシュの評価」**で、それは境界で間違い、しかも**間違いを
説明できません。**

「なぜこの地点の評価がこうなのか」に「500m 北のメッシュの値です」と答える
サービスにはしません。

### 案 B：母集団の分布を貯める（採用）

```
benchmark_distributions(scope_kind, scope_key, metric, profile, radius_m, …,
                        boundaries double precision[])
```

`_scope_statistics` の SQL を分解すると、こうなっています。

```sql
percentile_cont(ARRAY[0.25, 0.5, 0.75]) WITHIN GROUP (ORDER BY population)  -- 地点に依存しない
count(population)                                                            -- 地点に依存しない
count(*) FILTER (WHERE population <= 12430)                                  -- ★ ここだけ地点に依存
```

**依存しないほうを貯めます。** 昇順に並んだ値さえあれば、任意の値の位置は
二分探索で出ます。SQL の往復はゼロ。

行数は小さい。母集団（県で 4 種類＋市区町村ごとに 2 種類）× 指標 16 × プロファイル
× 半径。東京都・1 プロファイル・1 半径で **52 行**、全プロファイル・全半径でも
数千行です。

## 3. 事前計算できない母集団が 2 つある

```
nearby              この地点から10km以内の商圏
similar_population  商圏人口が同規模の商圏
```

**クリックした場所で母集団そのものが変わります。** 貯められません。その場で
測ります。

これは欠陥ではなく、**この 2 つがいちばん「その地点らしい」比較**だからです。
「県内で上位」ではなく「この辺で上位」を答えるための母集団で、地点に依存するのは
当然です。

事前計算できるのは 8 つのうち 6 つ。**位置づけに使う `urban`（市街地）は
事前計算できる側**なので、目的は達しています。

---

## 4. 貯める形：全部か、格子か

```sql
boundaries  double precision[]   -- 昇順に並んだ値
is_exact    boolean
```

母集団が 4,000 以下なら**値を全部**入れます（`is_exact = true`）。順位も
percentile も厳密に出ます。超えたら 0.1 パーセンタイル刻みの格子に落とします。

**「5,448 件中 1 位」を「上位0.1%」と言えるかどうかが、この違いです。**
格子にすると分解能は刻みまでになります。市区町村の母集団は数十〜数百件なので、
そのまま持ったほうが安く、かつ正確です。

---

## 5. 速くしても答えが変わらないこと

**これが、この表を入れてよい唯一の理由です。** 速いだけで答えが変わるなら、
入れてはいけません。

実測：同じ地点について、事前計算した分布から出した位置と、その場で測った位置を
**78 通り（指標 × 母集団）** 突き合わせ、**食い違い 0**。
`test_the_stored_distribution_gives_the_same_answer_as_measuring_it` が
見張ります。

結果：

```
build_dataset 全体 119ms / SQL 52 往復
  母集団の形を測るぶん   14 往復 49ms  →  6 往復 11ms
```

残った 6 往復は、上の「事前計算できない 2 つの母集団」と、サンプルデータに
`area_label` が無いため市区町村の分布が作れなかったぶんです。**本番データでは
市区町村ぶんも貯まります。**

Supabase（1 往復 10〜30ms）では、この 8 往復の差がそのまま 0.1〜0.25 秒です。

---

## 6. 無ければ、その場で測る

事前計算が無い県でも動きます。`stored_distributions` が空を返し、これまでどおり
測りに行きます。**新しく県を読み込んだ直後に位置づけが出ないより、遅いほうが
ましです。**

何をその場で測ったかは `measures.primary_benchmark.measured_live` に残ります。
書いておかないと、「なぜこの地点だけ遅いのか」に後から答えられません。

---

## 7. 実行の順番

```
kaigyou-etl refresh-stats
kaigyou-etl compute-scores --all-profiles
kaigyou-etl compute-benchmarks        ← 追加
```

**`compute-scores` のあとです。** この計算は `mesh_scores` を読みます。逆に
すると、古いスコアの分布が残ります。

---

## 8. まだ作っていない表

### `mesh_positioning`（地域特徴ベクトル・類似地域）

指示書 §8・§13。**これは案 A の形ですが、用途が違います。**

クリックした地点の評価には使いません（上の理由）。使うのは
**「この商圏と似ている地域はどこか」**の検索です。そこではメッシュ重心が
比較の単位なので、メッシュごとに貯めるのが正しい形になります。

作る前に決めることがあります。**どの軸で似ていれば「似ている」のか。**
人口と昼間人口が近くても、片方が学生街で片方が工業団地なら、開業判断としては
似ていません。距離の定義を決めずに作ると、**似ていない地域が似ていることに
なります。**

### メッシュごとの評価キャッシュ

いまは地点ごとに計算します。実測 119ms のうち、位置づけの計算は Python 側で
20ms 未満です。**貯める理由がまだありません。**
