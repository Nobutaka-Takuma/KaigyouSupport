# 問いのセンス

開発指示書 §49〜§66 への実装。

---

## 1. 何が問題だったか

同じ地点（沼津）の分析から、この 2 つが並んで出ていました。

**毎回、検索していたもの**

> 沼津市内の歯科衛生士・歯科医師の年齢構成は
> 在宅療養支援歯科診療所の届出数、訪問診療の実施医院数は

**答えは公表されていません。** 医師・歯科医師・薬剤師統計は都道府県単位まで
で、市区町村別の年齢階級はありません。施設基準の届出も、歯科の在宅療養支援
診療所を市区町村別に数えられる形では公表されていません。

そして、**それは調べる前から分かっていました。** それでも分析のたびに検索
していました。検索の上限は決まっているので、ここに使ったぶんは答えの出る
問いに回っていません。

**当たりだったもの**

> 復興土地区画整理事業中央工区の保留地の有無・住宅供給計画は、
> 将来推計人口の減少を緩和しうる規模か

手元の将来推計人口（減少）と、周辺スキャンで見つけた事実（区画整理事業＝
住宅供給）を突き合わせ、**「推計はこの供給を織り込んでいる」という前提**を
疑っています。答えが「保留地がまだ大量に残っている」なら、減少を前提にした
立地判断そのものが変わります。

前者は知識が増えます。後者は判断が変わります。

---

## 2. 良い問いの定義

> **既に持っているデータから「見落とされている重要な前提」を発見し、
> その前提を外部情報によって検証できる問い**

構造はいつも同じです（指示書 §51・§58）。

```
既存データ
　↓
特徴・違和感・矛盾・変化
　↓
重要な前提（ASSUMPTION）   ← ここが無かった
　↓
「本当にそうなのか？」
　↓
検証可能な問い
```

---

## 3. 直したこと

### 3.1 ASSUMPTION を第一級にした

これまでの連鎖は `FACT → PATTERN → QUESTION` でした。**前提の段がありません。**
無いと、問いは「なぜ若年層が多いのか」で止まります。悪くはありませんが、
判断は動きません。動くのは「この将来人口推計を、そのまま開業判断の前提に
してよいか」のほうです。前者はデータの説明を求め、**後者はデータの信用を
問うています。**

```python
class Assumption(BaseModel):
    id: str            # A001
    statement: str     # 「将来推計人口は、この地区の住宅供給を織り込んでいる」
    rests_on: list[str]  # その前提を置いている FACT / PATTERN
    if_wrong: str      # 外れていたら、どの判断がどう変わるか
```

STEP1 のプロンプトは、**問いより先に前提を書き出させます。** 前提は、いちばん
重い数字のところに置かれています——将来推計人口・昼間人口・競合数・地価。
判断を左右する数字ほど、その裏に確かめていない前提があります。

### 3.2 `researchability` が、検索するかどうかを決める

```
high    官公庁・自治体・事業者が公表している見込みが高い
medium  あるかもしれないが、粒度や公開範囲が読めない
low     公表されていないと分かっている  →  **検索しません**
```

`low` の問いは検索に回さず、そのまま「開業前に現地で確かめること」になります
（指示書 §56）。**`low` を付けることは失敗ではありません。** 重要なのに
調べられない問いは確かにあります。それを無理に検索して「その統計は存在
しません」という報告を持ち帰るより、最初から現地確認に回すほうが、正確で、
速く、安い。

### 3.3 調べても出ないことの台帳（`config/dead_ends.yaml`）

これが「なぜ毎回調べるのか」への直接の答えです。**分かっていることを、
モデルに渡していませんでした。**

```yaml
- topic: 市区町村単位の歯科医師・歯科衛生士の年齢構成
  why: 医師・歯科医師・薬剤師統計は都道府県単位まで。市区町村別の年齢階級は無い
  instead: 都道府県単位なら使える。市区町村の事情は、医院の開設年を承継リスクの代理に
```

STEP1 のプロンプトに差し込まれます。**`instead` を空にしないでください**——
塞ぐだけでは、次に何を問えばよいかが分かりません。

**育て方は「機械が測り、人が決める」。**

```
kaigyou-etl analyze --questions
```

の最後に、検索に回して繰り返し空振りしている問いが並びます。追加するかは
人が決めます。**機械が勝手に塞ぐと、あとから公表され始めたものに永久に
気づけません。**

### 3.4 塞いだつもりで塞げていない穴を塞いだ

`questions`（id 付き）と `research_questions`（古い文字列の並び）は、同じ問いを
別の形で持っています。**片方だけ落としても、STEP2 の調査プロンプトは「この
PATTERN の research_questions にだけ答えてください」と言うので、そのまま
検索されます。** 画面にもレポートにも何も出ません。両方から落とします。

### 3.5 問いの発生理由を残す（§57）

```python
class QuestionTrigger(BaseModel):
    type: TriggerType     # data_external_conflict / present_future_conflict / ...
    facts: list[str]      # 突き合わせた事実。**2 つ以上**
    reason: str
```

**1 つの事実からしか出ていない問いは、突き合わせではありません。** 検算が
落とします。「若年人口が多い」だけからは「なぜ若者が多いのか」しか出ず、
それは地域紹介の質問です。

### 3.6 検算（`verify_step1`）が落とすもの

| | なぜ |
|---|---|
| `already_in_data: true` の問い | 手元にある答えを外部に訊きに行っている（§62） |
| `decision_levers` が空の問い | 答えが出ても何も動かない（§59） |
| `researchability: low` で理由が無い問い | 現地確認へ回す判断の根拠が残らない（§56） |
| `trigger.facts` が 1 件以下 | 突き合わせではない（§58） |
| 存在しない ASSUMPTION を指す問い | 連鎖が切れる |

**古い形（`questions` が空）には掛けません。** 掛けると、問いを第一級にする
前に保存されたジョブが再実行のたびに落ちます。

## 4. レポートに出る形

```
### Q001　復興土地区画整理事業中央工区の保留地・住宅供給計画は、
　　　　　 将来推計人口の減少を緩和しうる規模か

**疑っている前提**　将来推計人口は、この地区の住宅供給計画を織り込んでいる
　外れていた場合：人口が増える側に振れ、減少を前提にした立地判断が成り立たなくなる

**この問いが出たわけ**（手元のデータと、外部で見つかった事実が食い違う）

- 将来推計人口は2040年まで一貫して減少予測
- 中央工区で復興土地区画整理事業が進行中
- → 住宅供給が推計に織り込まれているかを確かめられる

**答えが出ると何が変わるか**　減少を前提にした立地判断そのものが変わる
**何を調べれば答えが出るか**　市の区画整理事業計画書（保留地の残数と計画戸数）

- **H001** 保留地の住宅供給は減少を部分的に緩和する規模である
  判定：（2 周目に調べ直して）一部が支持された
```

**問いだけを並べると、なぜそれを訊いたのかが分かりません。** そこが、この
文書と生成 AI が書いた地域紹介との違いです。

## 5. 測る

`analyze --questions` に足しました。

```
  前提を疑って生まれた問い      12 件  (63%)
    うち判断が動いた             8 件

  問いの生まれ方ごと
    生まれ方                          問い  答えが出た  判断が動いた
    data_external_conflict              7          6            5
    deviation_from_peers                6          4            2
    （記録なし）                        6          3            1
```

**これが「問いのセンス」を測れる唯一の形です。** 手元のデータと外部の事実が
ぶつかって出た問いと、思いついて出た問いのどちらが効いたのかは、やってみない
と分かりません。LLM に「この問いは良い問いですか」と訊いても、それは問いを
出したのと同じモデルの意見です。

現地へ回した問い（`researchability: low`）は**空振りに数えません。** あれは
判断であって、失敗ではありません。空振りに数えると、正しく判断するほど成績が
下がります。

## 6. やらなかったこと

指示書 §55 は 5 つの評価軸を挙げています
（importance / researchability / decision_impact / novelty / evidence_potential）。

**このうち動作を変えるのは 2 つだけにしました。**

- `researchability` … 検索するかどうかを決めます
- `decision_levers` … 空なら問いとして通しません

`importance` は順序づけに使います。`novelty` と `evidence_potential` は欄に
していません——前者は `already_in_data` が、後者は `researchability` が同じ
ことを判定しており、**動作を変えない数字を並べると、埋めることが目的に
なります。** 5 つ揃っていることより、2 つが本当に効いていることを採りました。

必要になったら足せます。足す前に、`--questions` で「いまの 2 つで足りて
いないか」を見てください。
