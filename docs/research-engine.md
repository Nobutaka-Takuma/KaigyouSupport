# 地域リサーチAIへの機能強化

開発指示書「AI地域リサーチエンジン」に対する、現状の差分と実装の順序。

---

## 1. 現状はどこまで来ているか

指示書 §5 の推論パイプラインと、いま動いているものを突き合わせます。

| 指示書 | 現状 | 判定 |
|---|---|---|
| FACT | `Fact`（id・値・単位・出典キー） | 済 |
| BENCHMARK | measures が母集団6つの比較を持つ | 済 |
| PATTERN | `Pattern`（層を跨ぐことを検算で強制） | 済 |
| **QUESTION** | `Pattern.research_questions: list[str]` | **不足** |
| **HYPOTHESIS** | `Hypothesis`（`pattern_id` に紐づく） | **不足** |
| RESEARCH | STEP2 が PATTERN ごとに Web 検索 | 概ね済 |
| **EVIDENCE** | `Hypothesis.evidence: list[str]` | **不足** |
| **VERIFICATION** | `HypothesisStatus` 3値 | **不足** |
| INSIGHT | STEP3 `DemandInsight` | 済 |
| IMPLICATION | STEP3 `DemandMechanism` / `PatientSegment` | 済 |
| ACTION | STEP3 `BusinessDecision` / `actions` | 済 |

**両端はできていて、真ん中が薄い。** GIS との差がつくのはまさにその真ん中
（§30「WHY / SO WHAT の自動調査レイヤー」）なので、そこから直します。

---

## 2. いちばん重い不足：**反証を表現できない**

```python
HypothesisStatus = Literal["SUPPORTED", "PARTIALLY_SUPPORTED", "UNSUPPORTED"]
```

`UNSUPPORTED` が 2 つの別々のことを兼ねています。

1. 調べたが、支持する情報が**見つからなかった**
2. 調べたら、**違うと分かった**

経営判断にとってこの 2 つは正反対です。1 は「まだ分からないので現地で確かめる」、
2 は「その筋は消えたので別の筋を追う」。同じ札に入れると、レポートを読んだ人は
どちらなのか判断できません。**このプロジェクトが「0 と NULL は違う」と言って
きたのと同じ話です。**

指示書 §12 は `contradicted` を明示的に求めています。

さらに:

```python
evidence: list[str] = Field(..., min_length=1)
```

- **向きがありません。** どの証拠が支持で、どれが反証かが残りません
  （§11 の JSON 例は `"supports": true` を持っています）。
- **1 つ以上を強制しています。** 調べて何も出てこなかった仮説を、正直に
  記録できません。関係のない外部事実を引くか、仮説ごと捨てるかになります。
  **捨てると「調べていない」と区別がつかなくなります。**

---

## 3. 次に重い不足：**QUESTION が第一級でない**

いまの質問は `Pattern.research_questions: list[str]`、ただの文字列です。

- id が無いので、**下流から参照できません。** 「H003 は Q002 への答え」と
  書けず、仮説と質問の対応が人間の読み取りに委ねられます。
- **答えられたかどうかを数えられません。** 「7つ問いを立て、5つに答えが出た」
  が言えません（指示書 §25 の画面はこれを出す前提です）。
- §10 が求める「**この仮説を検証するために何を調べるべきか**を AI 自身が
  判断する」が、質問の中に暗黙に入っているだけで、独立した項目になって
  いません。

---

## 4. 実装したもの（第1回・済）

指示書 §27 の MVP ループを、**すでにある両端の間を埋める形で**閉じます。

### 4.1 QUESTION を第一級にする（済）

```python
class Question(BaseModel):
    id: str                    # Q001
    pattern_id: str            # どの PATTERN から出た問いか
    question: str              # なぜこうなっているのか
    why_it_matters: str        # 答えが出ると、何の判断が変わるのか
    what_would_answer_it: str  # 何を調べれば答えが出るのか（§10）
```

`what_would_answer_it` が「調査すべきことを AI 自身に決めさせる」（§16）の
実体です。**問いを立てた段で、調べ方まで決めさせます。** 次の段に丸投げすると
「〇〇駅について検索してください」になり、§23 が禁じているものになります。

`Pattern.research_questions`（文字列）は残します。**古いジョブの読み出しを
壊さないため**で、新しい `questions` があればそちらを使います
（expand → migrate → contract）。

### 4.2 EVIDENCE に向きを持たせる（済）

```python
class EvidenceLink(BaseModel):
    fact_id: str
    stance: Literal["supports", "contradicts", "context"]
    note: str      # その事実がなぜ支持／反証になるのか
```

`context` を入れるのは、**「関係はあるが判定には効かない」を捨てさせない**
ためです。捨てさせると、判定に効かない事実を無理に supports に入れます。

### 4.3 VERIFICATION の語彙を分ける（済）

```python
HypothesisStatus = Literal[
    "SUPPORTED",            # 支持する外部事実がある
    "PARTIALLY_SUPPORTED",  # 一部だけ確かめられた
    "UNCERTAIN",            # 調べたが、どちらとも言えない
    "CONTRADICTED",         # 調べたら、違うと分かった
    "UNSUPPORTED",          # 旧。読み出しのためだけに残す
]
```

`CONTRADICTED` と `UNCERTAIN` を足し、`UNSUPPORTED` は**読む側だけ**が
受け付けます（新しい出力では使わせません）。

`evidence` の `min_length=1` を外します。**調べて何も出なかったことを、
そのまま書けるようにするため**です。ただし `UNCERTAIN` 以外は 1 つ以上、
という検算を入れます——「支持されている」と言うなら根拠が要ります。

### 4.4 仮説を問いに紐づける（済）

`Hypothesis.question_id` を足します。これで、

- どの問いに、どの仮説が、どの証拠で答えたか
- どの問いが**答えられずに残ったか**

が機械的に追えます。

### 4.5 答えの出なかった問いを構造化する（済）

```python
class UnansweredQuestion(BaseModel):
    question_id: str
    why: str                   # なぜ答えが出なかったのか
    what_would_settle_it: str  # 何があれば決着するのか（現地確認・自治体照会など）
```

いまの `unanswered: list[str]` は自由文で、**次に何をすればよいかが残りません。**
ここは「開業前に現地で確認すべきこと」（§15）に直結します。

## 5. この回でやらないこと

指示書は 30 節ありますが、一度に作りません（§27）。

- **§25 の段階表示画面**（「5つのパターンを発見しました」…）。今回はデータの
  形を整える回で、画面は次。ただし数えられる形にはします。
- **§21 の中間 JSON をファイルに分ける**。`analysis_steps` に段ごとの出力を
  すでに JSON で保存しているので、実質は満たしています。ファイル分割は
  デバッグの都合であって、能力ではありません。
- **RESEARCH の反復**（調べた結果を見て、もう一度問いを立て直す）。これは
  効きますが、1 件あたりの API 費用と実行時間が跳ねます。まず 1 周を
  正しく閉じてから。

---

## 6. 壊さないための約束

歯科版は商談で使われています。

- **古い形の保存済みレポートが、そのまま読めること。** 読む側は
  `questions` が無い出力も、`evidence` が文字列の配列である出力も受け付けます。
- **STEP3 以降の入力の形を変えないこと。** 新しい欄は足すだけで、
  既存の欄の意味を変えません。
- 検算（trace）は新しい欄にも掛けますが、**古い形には掛けません。**

---

## 7. レポートに出る形

`## 調査の記録` として、本文のあとに付きます。**結論だけでなく、そこへ
至った道筋を読み手が確かめられること**が目的です。

```
## 調査の記録

この商圏について **2 件の問い**を立て、**1 件**に外部情報で答えが出ました。

### Q001　なぜ20〜39歳が周辺より15ポイント多いのか

**答えが出ると何が変わるか**　夜間の需要を住民数から見積もれるかが変わる。
**何を調べれば答えが出るか**　大学の公式サイトの学部所在地一覧と、市の住宅着工統計

- **H001** 大学の学生が若年人口を作っている
  判定：一部が支持された
  - 支持　1km圏に大学の校地があり、収容定員は約8,000人（C001）
  - 反証　当該校地は3・4年次のみが通う（C002）

### 答えが出なかった問い（開業前に確かめること）

**Q002　昼間人口を生んでいるのは就業者か通学者か**
- 決着させるには：平日12時台と18時台に現地で、駅から候補地方向への歩行者数を数える
```

**「答えが出なかった問い」が、そのまま現地確認の項目になります。** 指示書 §15 の
「開業前に現地確認すべきポイント」は、ここから出てきます。

## 8. 次の回

1. **§25 の段階表示**。「2件の問いを立て、1件に答えが出ました」は数えられる
   形になったので、画面に出せます。
2. **RESEARCH の反復**。調べた結果を見て、問いを立て直す 2 周目。効きますが、
   1 件あたりの費用と時間が跳ねるので、1 周を正しく閉じてから。
3. **QUESTION の品質**。いまは PATTERN ごとに 1〜3 個を LLM が出します。
   出た問いが凡庸かどうかを、あとから評価できる形にしたい（保存はされて
   いるので、材料は貯まります）。
