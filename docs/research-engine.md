# 地域リサーチAIへの機能強化

開発指示書「AI地域リサーチエンジン」に対する、現状の差分と実装の順序。

---

## 1. 現状はどこまで来ているか

指示書 §5 の推論パイプラインと、いま動いているものを突き合わせます。

| 指示書 | 現状 | 判定 |
|---|---|---|
| FACT | `Fact`（id・値・単位・出典キー） | 済 |
| BENCHMARK | measures が母集団6つの比較を持つ | 済 |
| PATTERN | `Pattern`（層を跨ぐことを検算で強制） | 済 |
| **QUESTION** | `Pattern.research_questions: list[str]` | **不足** |
| **HYPOTHESIS** | `Hypothesis`（`pattern_id` に紐づく） | **不足** |
| RESEARCH | STEP2 が PATTERN ごとに Web 検索 | 概ね済 |
| **EVIDENCE** | `Hypothesis.evidence: list[str]` | **不足** |
| **VERIFICATION** | `HypothesisStatus` 3値 | **不足** |
| INSIGHT | STEP3 `DemandInsight` | 済 |
| IMPLICATION | STEP3 `DemandMechanism` / `PatientSegment` | 済 |
| ACTION | STEP3 `BusinessDecision` / `actions` | 済 |

**両端はできていて、真ん中が薄い。** GIS との差がつくのはまさにその真ん中
（§30「WHY / SO WHAT の自動調査レイヤー」）なので、そこから直します。

## 2. いちばん重い不足：**反証を表現できない**

```python
HypothesisStatus = Literal["SUPPORTED", "PARTIALLY_SUPPORTED", "UNSUPPORTED"]
```

`UNSUPPORTED` が 2 つの別々のことを兼ねています。

1. 調べたが、支持する情報が**見つからなかった**
2. 調べたら、**違うと分かった**

経営判断にとってこの 2 つは正反対です。1 は「まだ分からないので現地で確かめる」、
2 は「その筋は消えたので別の筋を追う」。同じ札に入れると、レポートを読んだ人は
どちらなのか判断できません。**このプロジェクトが「0 と NULL は違う」と言って
きたのと同じ話です。**

指示書 §12 は `contradicted` を明示的に求めています。

さらに:

```python
evidence: list[str] = Field(..., min_length=1)
```

- **向きがありません。** どの証拠が支持で、どれが反証かが残りません
  （§11 の JSON 例は `"supports": true` を持っています）。
- **1 つ以上を強制しています。** 調べて何も出てこなかった仮説を、正直に
  記録できません。関係のない外部事実を引くか、仮説ごと捨てるかになります。
  **捨てると「調べていない」と区別がつかなくなります。**

---

## 3. 次に重い不足：**QUESTION が第一級でない**

いまの質問は `Pattern.research_questions: list[str]`、ただの文字列です。

- id が無いので、**下流から参照できません。** 「H003 は Q002 への答え」と
  書けず、仮説と質問の対応が人間の読み取りに委ねられます。
- **答えられたかどうかを数えられません。** 「7つ問いを立て、5つに答えが出た」
  が言えません（指示書 §25 の画面はこれを出す前提です）。
- §10 が求める「**この仮説を検証するために何を調べるべきか**を AI 自身が
  判断する」が、質問の中に暗黙に入っているだけで、独立した項目になって
  いません。

## 4. 実装したもの（第1回・済）

指示書 §27 の MVP ループを、**すでにある両端の間を埋める形で**閉じます。

### 4.1 QUESTION を第一級にする（済）

```python
class Question(BaseModel):
    id: str                    # Q001
    pattern_id: str            # どの PATTERN から出た問いか
    question: str              # なぜこうなっているのか
    why_it_matters: str        # 答えが出ると、何の判断が変わるのか
    what_would_answer_it: str  # 何を調べれば答えが出るのか（§10）
```

`what_would_answer_it` が「調査すべきことを AI 自身に決めさせる」（§16）の
実体です。**問いを立てた段で、調べ方まで決めさせます。** 次の段に丸投げすると
「〇〇駅について検索してください」になり、§23 が禁じているものになります。

`Pattern.research_questions`（文字列）は残します。**古いジョブの読み出しを
壊さないため**で、新しい `questions` があればそちらを使います
（expand → migrate → contract）。

### 4.2 EVIDENCE に向きを持たせる（済）

```python
class EvidenceLink(BaseModel):
    fact_id: str
    stance: Literal["supports", "contradicts", "context"]
    note: str      # その事実がなぜ支持／反証になるのか
```

`context` を入れるのは、**「関係はあるが判定には効かない」を捨てさせない**
ためです。捨てさせると、判定に効かない事実を無理に supports に入れます。

### 4.3 VERIFICATION の語彙を分ける（済）

```python
HypothesisStatus = Literal[
    "SUPPORTED",            # 支持する外部事実がある
    "PARTIALLY_SUPPORTED",  # 一部だけ確かめられた
    "UNCERTAIN",            # 調べたが、どちらとも言えない
    "CONTRADICTED",         # 調べたら、違うと分かった
    "UNSUPPORTED",          # 旧。読み出しのためだけに残す
]
```

`CONTRADICTED` と `UNCERTAIN` を足し、`UNSUPPORTED` は**読む側だけ**が
受け付けます（新しい出力では使わせません）。

`evidence` の `min_length=1` を外します。**調べて何も出なかったことを、
そのまま書けるようにするため**です。ただし `UNCERTAIN` 以外は 1 つ以上、
という検算を入れます——「支持されている」と言うなら根拠が要ります。

### 4.4 仮説を問いに紐づける（済）

`Hypothesis.question_id` を足します。これで、

- どの問いに、どの仮説が、どの証拠で答えたか
- どの問いが**答えられずに残ったか**

が機械的に追えます。

### 4.5 答えの出なかった問いを構造化する（済）

```python
class UnansweredQuestion(BaseModel):
    question_id: str
    why: str                   # なぜ答えが出なかったのか
    what_would_settle_it: str  # 何があれば決着するのか（現地確認・自治体照会など）
```

いまの `unanswered: list[str]` は自由文で、**次に何をすればよいかが残りません。**
ここは「開業前に現地で確認すべきこと」（§15）に直結します。

## 5. この回でやらないこと

指示書は 30 節ありますが、一度に作りません（§27）。

- **§25 の段階表示画面**（「5つのパターンを発見しました」…）。今回はデータの
  形を整える回で、画面は次。ただし数えられる形にはします。
- **§21 の中間 JSON をファイルに分ける**。`analysis_steps` に段ごとの出力を
  すでに JSON で保存しているので、実質は満たしています。ファイル分割は
  デバッグの都合であって、能力ではありません。
- **RESEARCH の反復**（調べた結果を見て、もう一度問いを立て直す）。これは
  効きますが、1 件あたりの API 費用と実行時間が跳ねます。まず 1 周を
  正しく閉じてから。

## 6. 壊さないための約束

歯科版は商談で使われています。

- **古い形の保存済みレポートが、そのまま読めること。** 読む側は
  `questions` が無い出力も、`evidence` が文字列の配列である出力も受け付けます。
- **STEP3 以降の入力の形を変えないこと。** 新しい欄は足すだけで、
  既存の欄の意味を変えません。
- 検算（trace）は新しい欄にも掛けますが、**古い形には掛けません。**

## 7. レポートに出る形

`## 調査の記録` として、本文のあとに付きます。**結論だけでなく、そこへ
至った道筋を読み手が確かめられること**が目的です。

```
## 調査の記録

この商圏について **2 件の問い**を立て、**1 件**に外部情報で答えが出ました。

### Q001　なぜ20〜39歳が周辺より15ポイント多いのか

**答えが出ると何が変わるか**　夜間の需要を住民数から見積もれるかが変わる。
**何を調べれば答えが出るか**　大学の公式サイトの学部所在地一覧と、市の住宅着工統計

- **H001** 大学の学生が若年人口を作っている
  判定：一部が支持された
  - 支持　1km圏に大学の校地があり、収容定員は約8,000人（C001）
  - 反証　当該校地は3・4年次のみが通う（C002）

### 答えが出なかった問い（開業前に確かめること）

**Q002　昼間人口を生んでいるのは就業者か通学者か**
- 決着させるには：平日12時台と18時台に現地で、駅から候補地方向への歩行者数を数える
```

**「答えが出なかった問い」が、そのまま現地確認の項目になります。** 指示書 §15 の
「開業前に現地確認すべきポイント」は、ここから出てきます。

## 8. 実装したもの（第2回・済）：§25 の段階表示

待っている数分に画面へ出ていたのは、これだけでした。

```
2 / 4 ステップ完了 — STEP2 実行中 3分12秒
```

**動いていることは分かっても、何かを見つけているのかは分かりません。**
ところが STEP1 の出力——パターンと問い——は、その段が終わった時点でもう DB に
あります。レポートが書き上がるまで、誰にも見せていなかっただけです。

`GET /api/analysis/{job_id}` が `progress` を返すようにしました。

```
ここまでに分かったこと
  統計から 5 件のパターンを見つけ、3 件の問いを立てました。
  そのうち 2 件 に、外部情報で答えが出ました。
  仮説 4 件  [支持された 1] [一部が支持された 1] [調べたら違うと分かった 1] …
  引用した外部資料 5 件（うち官公庁・政府統計などの一次資料 3 件）

  確かめられなかったこと（開業前に現地で）
  - 昼間人口を生んでいるのは就業者か通学者か
    → 平日12時台と18時台に現地で、駅から候補地方向への歩行者数を数える
```

### 8.1 数えるのは 1 か所（`kaigyou_intel/coverage.py`）

画面とレポート冒頭の「この分析で確かめたこと」は、同じ `coverage.tally` を
通ります。**別々に数えさせません。** 待っている間に見た「答えが出た 5 件」と、
出来上がった文書の「4 件」が食い違うと、どちらが正しいのかを読み手が確かめる
術はありません。確かめられない食い違いは、数字そのものへの信用を落とします。

### 8.2 「まだ」と「0 件」を分ける

- STEP2 が走っている最中に「答えが出た 0 件」を出しません（`researched`）。
- 出なかった判定を「調べたら違うと分かった 0」として並べません。0 件は
  「その判定が出なかった」であって「0 という結果が出た」ではありません。
- 問いを記録していない頃のジョブでは、節ごと出しません（`progress: null`）。
  「問い 0 件」は**「調べていない」に見えます**が、実際は「この版では記録して
  いない」です。

### 8.3 ついでに直したこと

進捗の問い合わせは 4 秒ごとに走ります。その応答に各段の `output_json` が
乗っていましたが、**どの画面も読んでいませんでした。** 落としました。全文が
要るときは `kaigyou-etl analyze --show` が DB から直接読みます。

## 9. 実装したもの（第3回・済）：RESEARCH の反復

1 周目は STEP1 が立てた問いを、そのまま検索に持っていきます。実際の調査は
そうではありません。**1 回目に何が出てこなかったかを見て、次に何を引くかが
決まります。**

いちばん効くのは `CONTRADICTED` です。

> H001　タワーマンション供給が子育て世帯を呼び込んだ
> 判定：**違うと分かった**（供給は2010年代前半で、増加はそれ以降）

**問いはまだ生きています。** 人がやるなら「では何が本当の理由なのか」と続ける
ところで、1 周目で止まるとそこで終わりになります。

### 9.1 走る条件

`limits.research_rounds: 2`（既定）で、**1 周目が何かを残したときだけ**。

- `open_questions` がある、または
- `CONTRADICTED` の仮説がある

全部に答えが出ていれば走りません。走らせても足すものが無く、費用と時間だけが
増えます。`research_rounds: 1` で完全に止まります。

### 9.2 検索で決着しないものには手を出さない

`what_would_settle_it` が「現地で歩行者数を数える」「自治体に照会する」で
あるものは、**何回検索しても答えは出ません。** プロンプトでそこを明示的に
外させています。そういう問いは未確認のまま残り、そのまま「開業前に現地で
確かめる項目」になります。それは失敗ではなく、この調査の結論の一部です。

### 9.3 壊れやすいところ

**id の衝突。** どちらの周も `C001` / `H001` から採番します。そのまま足すと、
2 周目の C001 が 1 周目の C001 を指しているように読め、根拠の追跡が静かに
壊れます。**見た目には何も起きません**——レポートには「C001 による」と出て、
別の事実が引かれているだけです。合流時に振り直し、`evidence` と
`evidence_links.fact_id` も付け替えます。

**検算を 2 周目だけ緩めないこと。** 緩めると「支持された」と書いてあるのに
支持の根拠が無い仮説が混ざります。かといって落として例外を上げると、既に
払った 1 周目まで消えます。**2 周目のほうを捨てて、理由を `unanswered` に
残します。** 呼び出しの失敗・本文が空・JSON に写せなかった場合も同じです。

**答えが出た問いを未確認に残さないこと。** 2 周目で決着した問いは
`open_questions` から外します。残すと、答えが出ているのに現地確認の項目として
並び続けます。

### 9.4 費用

**測っていません。**設定した予算から言えるのはここまでです：1 周目は最大 8
検索（`max_searches_total`）、2 周目は最大 3（`followup_searches`）。呼び出しは
2 回増えます（調べる・写す）。実測が出たら、ここを実測に書き換えてください。

### 9.5 レポートと画面に出る形

`round` を外部事実と仮説に持たせ、レポート冒頭と画面に出します。

```
- **1 周目で答えの出なかった問いを、角度を変えて調べ直しました**　→ 2 周目で立てた仮説 1 件
...
- **H002** 分譲ではなく賃貸の供給が単身勤務者を呼び込んだ
  判定：（調べ直して）支持された
```

**調べ直したという事実そのものが記録です。** 書かないと、1 周で出たように
読めます。

## 10. 実装したもの（第4回・済）：QUESTION の品質

問いは PATTERN ごとに 1〜3 個、LLM が出しています。**どれが筋の良い問いで、
どれが埋め草だったのかは、出た時点では分かりません。** 分かるのはあとからです。

```
$ kaigyou-etl analyze --questions
```

### 10.1 LLM に採点させません

「この問いは良い問いですか」と聞けば、それらしい点数が返ってきます。ですが
それは問いを出したのと同じモデルの意見で、外から確かめる手立てがありません。
このプロジェクトが「予測はしない、確かめられることだけ書く」と言ってきたのと
同じ理由で、ここも**実際に何が起きたか**だけを数えます。

追えるのは、調査の連鎖が繋がったからです。

    QUESTION → HYPOTHESIS（question_id）→ EVIDENCE（向き）→ 判定
             → changes / decision_impact（どの判断が動くか）

### 10.2 「答えが出た」を成績にしません

**答えが出ることと、判断が動くことは違います。** 実測で出た例：

> 「区画整理により計画的に形成された市街地である」

正しくても、診療コンセプトも設備も診療時間も変わりません。答えが出た件数だけを
数えると、こういう問いが良い問いとして数えられます。数えるのは
`changes` が付いた仮説に繋がった問いのほうです。

出る形：

```
問い 6 件（ジョブ 3 件）

  答えが出た                 4 件  (66%)
    うち一次資料が根拠       3 件
    うち 2 周目で決着        1 件
  現地で確かめる項目に       1 件  (16%)
    （検索では決着しない問い。失敗ではありません）

  判断が動いた               3 件  (50%)

  動いたもの
    患者層　2 件 ／ 診療時間　1 件 ／ 診療コンセプト　1 件

  プロンプト版ごと（問いを出す STEP1 の版）
    版              問い  答えが出た  判断が動いた
    step1-v1.10       5          3            2
    step1-v1.9        1          1            1

  答えも出ず、現地確認にも回らなかった問い 1 件
    Q002  駅の乗降客のうち何割が候補地方向へ歩くか
```

最後の一覧が、**次にプロンプトを直すときに読むところ**です。答えも出ず、
現地確認にも回らなかった問い——調べようがなかったのか、そもそも問いとして
弱かったのか。

### 10.3 数えないもの

- **`UNCERTAIN` は答えではありません。** 調べたが、どちらとも言えなかった。
- **現地に回った問いは失敗ではありません。** 検索では決着しない問いだった、
  というだけで、それはこの調査の結論の一部です。
- **問いを記録していない頃のジョブは母数に入れません。** 混ぜると、版の違いが
  「答えが出た割合の低下」に見えます。
- **版を跨いで平均しません。** 問いを出すプロンプトを直した前後で混ぜると、
  直した効果が薄まって見えます。

### 10.4 表を足していません

材料はすでに `analysis_steps.output_json` にあります。表を作ると、そこへ
書き込む経路と、古いジョブの埋め戻しと、ずれたときの直し方が要ります。
読むだけなら、いつでも数え直せます。

## 11. 指示書との差分（残り）

§27 の MVP ループは閉じました。残っているのは、いまのところ**急がないと
判断したもの**です。

- **§21 の中間 JSON をファイル分割**。`analysis_steps` に段ごとの出力を JSON で
  保存しているので、実質は満たしています。ファイル分割はデバッグの都合で
  あって、能力ではありません。
- **3 周目以降**。2 周目で決着しなかったものは、たいてい公表されていない
  ことです。回しても増えるのは費用と時間だけ、という見込みですが、
  `--questions` の「2 周目で決着」の件数が貯まれば確かめられます。
