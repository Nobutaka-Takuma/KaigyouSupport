# 速さ

**測ったものだけ書きます。** 見込みは見込みと書きます。

計測環境：手元の PostgreSQL 16（unix ソケット、1 往復 0.2ms）、開発用の
サンプルデータ。本番は Vercel（東京）から Supabase で、**1 往復 10〜30ms** です。

---

## 1. いちばん効いたもの：SQL の往復を減らす

手元で測ると、どのエンドポイントも数十 ms で返ります。**それは往復の代金を
隠しています。** 1 リクエストが SQL を何回往復しているかを数えました。

| | 前 | 後 |
|---|---:|---:|
| `/api/dataset`（分析の開始時に組み立てる） | **114** | **67** |
| `/api/candidate-analysis`（地図を 1 回クリック） | 45 | **31** |
| `/api/rankings` | 17 | 12 |

Supabase で 1 往復 15ms とすると、地図のクリックが **0.7 秒→0.5 秒**、分析の
開始が **1.7 秒→1.0 秒**。25ms なら差はその倍です。手元では 47 往復の差が
**10ms** にしかならないので、ここは測り方を変えないと見えません。

### 何を直したか

削った 47 往復のうち、**1 本も新しい機能を諦めていません。** 同じことを
訊き直していただけです。

1. **同じ問いを何度も訊いていた**（`db.column_exists` / `table_exists`）

   `mesh_scores.facility_category` があるかを、1 リクエストの中で **15 回**
   訊いていました。スキーマは 1 リクエストの間に変わりません。答えを
   **接続ごとに**覚えます（`db._SCHEMA_CACHE`）。

   接続は API ではリクエストごと、worker ではジョブごとに開き直すので、
   この記憶は次のリクエストまで生き延びません。**デプロイの窓**（コードが
   先に出て、マイグレーションは手で当てる）を守るという本来の目的は
   変わっていません。マイグレーションを当てたら `migrate()` が忘れます。

2. **まとめられる問いを 1 つずつ訊いていた**（`columns_that_exist` /
   `tables_that_exist`）

   14 列の有無を 14 往復で訊いていました。**問いが 14 個あることと、往復が
   14 回必要なことは別です。** 1 往復にしました。出典表の有無（5 表）も同じ。

3. **画面が同じものを 2 回取りに行っていた**（初回ロード 13 → 11 リクエスト）

   `prefecture` は最初 localStorage の値（初回は null）で、`/api/prefectures`
   が返ってから確定します。それを見ている効果が 2 回走り、1 回目の答えを
   捨てていました。**絞り込みの選択肢**（`specialties` /
   `city-planning/kinds`）は県が決まるまで待たせます。地図のレイヤは待たせて
   いません——そちらは 1 回目にも意味のある絵が出ます。

## 2. 分析：押してから最初の 1 歩まで、最大 60 秒 何も起きていなかった

cron は 1 分おきです。それは「1 分に 1 回進む」という意味であって、
「押してから 1 分待つ」という意味ではないはずでした。ところが**作ったジョブを
最初に拾うのも cron**なので、押してから最初の 1 歩までが最大 60 秒、平均 30 秒。
画面には「順番待ち」とだけ出ます。

`POST /api/analysis` が、応答を返したあとに自分で worker を起こします
（`_start_soon`）。鍵のある環境でだけ動き、失敗しても cron が次の分に拾います。

**段と段の間には、もう cron の待ちはありません。** `worker.tick` は残り時間が
足りるかぎり続けて回します（`invocation_seconds` − `reserve_seconds`）。

## 3. レポート生成：時間を決めているのは検索回数

これは以前からの実測（`config/analysis.yaml` のコメント）です。

- **検索回数がそのまま実行時間です。** サーバ側の検索ループは 1 回の呼び出しの
  中で回り、増えていく文脈を毎回読み直します。実測（沼津・4 検索）で入力
  794,572 トークン・5 分 36 秒。
- PATTERN ごとに呼び出しを分けて同時に走らせたので、直列の合計から
  **いちばん遅い 1 本**になりました。
- 実測（裾野・半径 1km）では 36 件の資料を取得して、本文が根拠に引いたのは
  7 件。**29 件は読むためだけに時間と金を使っています。**

### いま効く手

| 手 | 効き | 代償 |
|---|---|---|
| `limits.max_searches_total` を下げる | **直接効きます** | 調べる幅が狭くなる。ただし上限を絞ると「答えの出そうな問い」から使うので、引かれる資料の割合はむしろ上がります |
| `limits.research_rounds: 1` | 呼び出し 2 回と最大 3 検索ぶん | 「調べたら違うと分かった」で止まる |
| `limits.max_patterns` を下げる | 並列の本数が減るので**効きません**（律速はいちばん遅い 1 本） | 見つける特徴が減る |
| `steps.3/4.effort` を下げる | 生成時間が縮む | **ここは判断の段です。**下げるかどうかは出来を見てから |
| `KAIGYOU_CACHE_TTL=1h` | **速くなりません。** 費用の話です | 書き込み単価が 1.25→2 倍 |

**`effort` を下げる前に、`analyze --timing` で段ごとの実測を見てください。**
STEP2 が支配的なら effort を下げても変わりません。

## 4. まだ手を付けていないもの（見込み）

- **母集団 6 つの比較を 1 往復にまとめる。** `/api/dataset` の残り 67 往復の
  うち **14 往復**が、6 つの母集団に同じ形の問い合わせを繰り返しているぶん
  です（`measures.measure_scope_shape` 8 + `_scope_statistics` 6）。
  LATERAL か UNION ALL で 1 本にできる見込みですが、**比較の答えが変わって
  いないことを確かめる手当てが要ります。** ここは数字が正しいことのほうが
  速さより大事です。
- **`worker.reserve_seconds: 240` の見直し。** 1 ステップの最長の見込みです。
  実測より大きいと、予算が残っているのに次の段へ進まず、cron の次の呼び出し
  （最大 60 秒後）を待ちます。`analyze --timing` の実測が貯まったら詰めて
  ください。
- **`/api/data-status` の 22 往復。** 表ごとに件数を数えています。画面の
  「データソース一覧」でしか使わないので急ぎませんが、まとめられます。

## 5. 測り方

```
# 1 リクエストが SQL を何往復するか
python - <<'PY'
import sys, collections; sys.path.insert(0, "server")
import psycopg
n = collections.Counter(); _ex = psycopg.Cursor.execute
def execute(self, q, p=None, **kw):
    n["q"] += 1
    return _ex(self, q, p, **kw)
psycopg.Cursor.execute = execute
from fastapi.testclient import TestClient
from kaigyou_api.main import app
c = TestClient(app)
url = "/api/dataset?lat=35.6717&lng=139.7650&radius=1000"
c.get(url); n["q"] = 0; c.get(url)
print(n["q"], "往復")
PY

# 段ごとの所要時間・トークン・費用
kaigyou-etl analyze --timing
```

回帰は `test_building_a_dataset_does_not_ask_the_schema_over_and_over` が
見張ります（往復が 90 本を超えたら落ちます）。
