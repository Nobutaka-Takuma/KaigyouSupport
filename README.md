# KaigyouSupport — 歯科開業候補地分析 MVP

東京都内の任意地点について、周辺の**人口・年齢構成・人口動態・歯科医院の分布・駅アクセス**を
公的データから集計し、地図上で確認・比較するツールです。

> **中心機能は「地図上の任意地点を指定 → 商圏を自動分析」です。**
> ランキングは同じ分析エンジンをメッシュ全体に適用した副次機能として実装しています。

開業成功確率・売上・患者数・家賃の予測は行いません。

### 架空データを実データとして投入しない仕組み

取得できなかった情報源があれば、失敗内容が `acquisition_runs` に記録され、
`kaigyou-etl status` / `/about` 画面 / `GET /api/data-status` で常に確認できます。
該当テーブルは空のままで、代替データは投入されません。

動作確認用の合成データを使う場合（`kaigyou-etl generate-sample`）は:

- 情報源名が `【サンプル】` で始まり、`data_sources.dataset_kind = 'sample'`
- 全画面の上部に警告バナーが常時表示される（非表示不可）
- 分析APIが、合成データが**どのスコアに影響するか**を名指しで返す
- 同一テーブルに実データと合成データが同時に存在する状態（二重計上）を検知して警告

### 数値を読むときの注意

- **人口は国勢調査の常住人口（夜間人口）です。** 昼間人口・通勤流入は含みません。
  オフィス街・繁華街では実際の需要を大きく過小評価します
  （例: 丸の内1km商圏は常住人口6,764人に対し歯科医院156件）。
  該当する地点では分析パネルに警告を表示します。
- 商圏は直線距離の円です。鉄道・河川・幹線道路による分断は考慮していません。
- 歯科医院数は施設数であり、規模・ユニット数・診療実績は考慮していません。
- 国勢調査メッシュ統計は小規模メッシュに秘匿処理（隣接メッシュへの合算）が
  かかっています（東京都500mメッシュでは5,449件中543件）。合計値は保たれますが、
  局所的に人口配置が1メッシュ分ずれます。
- 乗降客数は駅単位の合算値です。同一駅の複数事業者を合計しています
  （新宿駅 = JR東・京王・小田急・メトロ・都営の合計 271万人/日）。
  最新年度に数値がない駅は、直近で数値のある年度を使い `passengers_year` に記録します
  （9,317駅中 2024年度が7,394駅、752駅は全年度で数値なし＝NULL）。
- 人口増減率は2015→2020年の変化です。
- エリア名はメッシュ中心点を含む市区町村です。湾岸の埋立地など、N03で
  「所属未定地」となっている場所に中心点が落ちる場合は最寄りの市区町村名を
  使います（豊洲・東雲の一部が該当）。

## 構成

```
External Data → ETL（download/validate/transform/load）→ PostGIS → API → Web UI
                 ↑ ネットワークに触れるのはここだけ
```

| ディレクトリ | 役割 |
|---|---|
| `config/` | データソース定義（`sources.yaml`）、スコアリング設定（`scoring.yaml`） |
| `db/migrations/` | PostGIS スキーマと分析関数（SQL） |
| `server/kaigyou_core/` | 設定・DB・メッシュ計算・スコアリング・出典管理（ETL と API の共通部品） |
| `server/kaigyou_etl/` | データ取得。**外部通信を行う唯一のコンポーネント** |
| `server/kaigyou_api/` | 読み取り専用 HTTP API。外部データを取得しない |
| `web/` | MapLibre GL JS + React のフロントエンド。API 以外と通信しない |
| `server/tests/` | 単体テスト＋PostGIS 結合テスト |
| `api/` | Vercel のサーバレス関数の入口（`kaigyou_api` を読み込むだけ） |

UI・API・ETL は別プロセスであり、UI からデータ取得処理を起動する経路はありません。

## セットアップ

必要なもの: Python 3.11+ / Node.js 20+ / PostgreSQL 16 + PostGIS 3（Docker 可）

```bash
# 1. 依存関係
make setup

# 2. データベース（Docker を使う場合）
make db
export DATABASE_URL=postgresql://kaigyou:kaigyou@127.0.0.1:5432/kaigyou

# 3. スキーマ適用
make migrate

# 4. 実データを投入（下記「実データを表示するまで」を参照）
kaigyou-etl load-local ~/Downloads

# 5. 起動
make api            # http://127.0.0.1:8000  （API ドキュメント /docs）
make web            # http://127.0.0.1:5173
```

## 実データを表示するまで

> **データベースの中身はリポジトリに含まれません。**
> `git clone` した直後のデータベースは空です。画面に
> 「公的データ未取得」「サンプルデータ表示中」と出ている場合は、
> このリポジトリに実データが入っていないのではなく、
> **お使いのデータベースにまだ投入していない**状態です。
> `data/raw/` も `.gitignore` 済みです（各提供元の利用規約に従うため）。

### 必要なファイルをダウンロードする（5情報源・6ファイル ＋ 任意2）

歯科診療所と人口メッシュはフォーム経由の配布です。S12・N03 は直リンクがあり
`kaigyou-etl run <source>` で自動取得も試せますが、手元にダウンロードしたものを
渡すのが確実です。

| データ | 入手先 |
|---|---|
| 歯科施設情報 CSV | 厚労省 [医療機能情報提供制度](https://www.iryou.teikyouseido.mhlw.go.jp/znk-web/juminkanja/S2400/initialize) |
| 国勢調査 500mメッシュ（最新年） | [e-Stat 統計GIS](https://www.e-stat.go.jp/gis/statmap-search?type=1) 東京都 |
| 国勢調査 500mメッシュ（前回） | 同上（人口増減率の基準に使用） |
| 経済センサス 500mメッシュ | 同上（従業者数・事業所数。昼の需要に使用） |
| OpenStreetMap 道路 shapefile（任意） | [Geofabrik](https://download.geofabrik.de/asia/japan.html) の `kanto-latest-free.shp.zip`（徒歩圏の商圏に使用） |
| 駅別乗降客数 zip | [国土数値情報 S12](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-S12.html) |
| 行政区域 zip | [国土数値情報 N03](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N03-v3_1.html) 東京都 |
| 地価公示 zip（任意） | [国土数値情報 L01](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-L01-v3_1.html) 東京都（`L01-26_13_GML.zip`） |

**ファイル名は変更不要です。** ダウンロードしたままの名前で構いません。
どのファイルがどの情報源かは、名前ではなく中身（CSVのヘッダ、統計表の列ID、
zip の中のファイル名）で判別します。同じ S12 の zip が配布元では
`S12-25_GML.zip`、ブラウザ経由では `S1225_GML.zip` になることがあるためです。

### 都道府県を追加する（東京都以外）

都道府県ごとに**別々に**取り込みます。同じフォルダに2県分のファイルを混ぜないでください
（同じ種類のファイルが2つあると片方しか使われません）。

静岡県（コード 22）を足す例:

```
download/13/  … 東京都のファイル
download/22/  … 静岡県のファイル
```

1. **県別のファイル**を静岡県ぶん取得して `download/22/` に置きます。
   - 国勢調査 500mメッシュ（最新年・前回年）… e-Stat の 統計GIS で「静岡県」を選択。
     ファイル名は `tblT001141H22.txt` のように末尾が `H22` になります
   - 経済センサス 500mメッシュ … 同上（`tblT001147H22.txt`）
   - 行政区域 N03 … `N03-20240101_22_GML.zip`
   - 地価公示 L01（任意）… `L01-26_22_GML.zip`
2. **全国共通のファイル**（歯科施設 CSV・駅別乗降客数 S12）は取り込み済みなので不要です。
   置かなくて構いません。
3. 取り込みます:

```powershell
python -m kaigyou_etl load-local download/22 --partial
```

`--prefecture` は**不要**です。都道府県は e-Stat のファイル名（`tblT001141H22.txt` の
`H22`）と N03 のファイル名から判定します。判定できない場合や、指定が
ファイル名と食い違う場合は、取り込まずにエラーで止まります。

> **取り込み先を間違えたときは** `python -m kaigyou_etl drop-prefecture --prefecture 22 --dry-run`
> で件数を確認し、`--yes` を付けて削除してから正しいファイルを入れ直してください。
> 誤った都道府県として入ったデータは「欠測」ではなく「別の県の実数」なので、
> 放置すると本物として読めてしまいます。

`--partial` は「歯科施設と駅のファイルが無い」ことを承知のうえで進めるための指定です。

> 駅データ（S12）は全国分が入っていますが、`stations.prefecture_code` は取り込み時点で読み込まれていたメッシュから決めているため、後から足した県の駅は空欄のままです。分析・スコアには影響しません（最寄り駅は距離で探すため）。表示を揃えたい場合は `python -m kaigyou_etl run mlit_stations --input <S12のzip>` で入れ直してください。

これで東京都のデータは残ったまま静岡県が追加され、画面の上部に
**都道府県の選択欄**が出ます（2件以上読み込まれたときだけ表示されます）。

地点をクリックしたときの分析は、**選択した都道府県ではなくクリックした地点の都道府県**で行われます（パネルに「分析対象: ○○県」と表示されます）。上部の選択欄は、地図の初期位置・境界レイヤ・ランキングの対象を切り替えるものです。

> **スコアは都道府県ごとに正規化しています。**
> 静岡県の総合スコア70と東京都の総合スコア70は別の意味です。
> ランキングは常に1県のなかでの順位で、県をまたいで混ぜることはしません。

### 1コマンドで投入する

6つのファイルを同じフォルダに置いて:

```bash
kaigyou-etl load-local <フォルダ>
```

Windows (PowerShell) の場合:

```powershell
.venv\Scripts\kaigyou-etl load-local .\download
```

`make` が使える環境なら `make load-local DIR=./download` でも同じです。

5情報源の取り込み → サンプルデータの削除 → スコア基準の再計算 →
メッシュスコアの再計算 → 取得状況の表示、までを順に実行します。
所要時間は約4分（取り込み25秒、スコア計算3分半）。

### 個別に実行する場合

```bash
kaigyou-etl run mhlw_dental_clinics   --input <歯科CSV>
kaigyou-etl run estat_population_mesh --input <最新年メッシュ> --baseline <前回メッシュ>
kaigyou-etl run mlit_stations         --input <S12 zip>

kaigyou-etl refresh-stats    # スコア基準を実データの分布で再計算
kaigyou-etl compute-scores   # ランキング・ヒートマップ用スコアを再計算
kaigyou-etl status           # 4/4 になっていることを確認
```

### 確認方法

```bash
kaigyou-etl status
```

`公的データを取得できた情報源: 4 / 4` と表示され、
`⚠ サンプル（合成）データ` の行が出なければ完了です。
ブラウザを再読み込みすると、画面上部の警告バナーが消えます。

`/about` 画面でも同じ内容（情報源ごとの件数・データ時点・取得日時）を確認できます。

### うまく表示されないとき

```bash
kaigyou-etl doctor
```

設定ファイル・DB接続・PostGIS・マイグレーション・投入件数・スコアを順に確認し、
最初に問題のある箇所と対処コマンドを表示します。

```
[OK  ] リポジトリの場所   /path/to/KaigyouSupport
[OK  ] データソース定義   config/sources.yaml
[NG  ] データベース接続   OperationalError: connection failed: ...
         → PostgreSQL が起動しているか、DATABASE_URL が正しいか確認してください。
```

画面に「APIエラー」と出る場合、そこに表示される内容がそのまま原因です。
よくあるもの:

| 表示 | 原因 | 対処 |
|---|---|---|
| `ConfigNotFound: 設定ファイルが見つかりません` | リポジトリ外から API を起動している | リポジトリ直下から起動するか `KAIGYOU_ROOT` を設定 |
| `OperationalError: connection failed` | DB未起動、または `DATABASE_URL` が違う | API を起動するシェルでも `DATABASE_URL` を設定 |
| `UndefinedColumn` / `UndefinedTable` | マイグレーション未適用 | `kaigyou-etl migrate` |

> **API サーバを起動するシェルでも `DATABASE_URL` が必要です。**
> ETL を実行したシェルと別のウィンドウで API を起動している場合、
> 環境変数が引き継がれていないことがあります。

### 動作確認だけしたい場合

実データを用意せずに画面を触りたいときは、合成データを投入できます。

```bash
kaigyou-etl generate-sample
kaigyou-etl refresh-stats && kaigyou-etl compute-scores
```

このデータは**実データではありません**。情報源名が `【サンプル】` で始まり、
全画面に警告バナーが常時表示されます（非表示にできません）。
実データを入れる前に `kaigyou-etl drop-sample` で削除してください
（`load-local` は自動で削除します）。

## 背景地図タイル

地図タイルは同梱していません。`web/.env` に設定してください
（未設定でも、自前のデータレイヤーのみで地図は動作します）。
`web/.env.example` の既定値は国土地理院の淡色地図で、APIキーもアカウントも要りません。

```
VITE_RASTER_TILES=https://cyberjapandata.gsi.go.jp/xyz/pale/{z}/{x}/{y}.png
VITE_RASTER_ATTRIBUTION=国土地理院
# ベクタタイルのスタイルJSONを使う場合は代わりに
VITE_BASEMAP_STYLE=https://example.com/style.json
```

`VITE_RASTER_ATTRIBUTION` は地図右下に常時表示されます。
タイル提供元の利用規約は出典表示を求めるのが通例なので、消さないでください。
これらはビルド時に埋め込まれるため、変更後は再ビルドが必要です。

## スマホから見る（デプロイ）

Vercel（静的ファイル＋API）と Supabase（PostGIS）に載せる手順は
**[docs/deploy.md](docs/deploy.md)** にあります。

構成は変わりません。データ取得（ETL）は手元のPCから Supabase に直接書き込み、
公開側は読むだけです。要点だけ：

- Supabase のリージョンは **Tokyo**。接続文字列は用途で使い分けます
  — 投入は **Session pooler (5432)**、Vercel からは **Transaction pooler (6543)**。
  どちらもホストは `pooler.supabase.com` で、ユーザ名は `postgres.<プロジェクトID>` です。
  `db.<ref>.supabase.co` の Direct connection は IPv6 専用なので使いません。
- Vercel の環境変数は `DATABASE_URL` と `VITE_RASTER_*` の3つ。
- `VITE_` で始まる変数はビルド時に埋め込まれるので、変更したら再デプロイが必要です。
- 公開URLは誰でも見られます。限定したいなら Vercel の Deployment Protection を有効に。

## データソースの詳細

各情報源の癖と、それに対してアダプタが何をしているか。

**歯科医院（取り込み実績あり）**
厚労省「医療機能情報提供制度」の歯科施設情報 CSV
（`0xx_dental_facility_info_YYYYMMDD.csv`、UTF-8 BOM付き、57列）。
ID / 正式名称 / 所在地 / 都道府県コード / 市区町村コード / 緯度 / 経度 を使用します。

> 実ファイルでは約6%（54,637件中3,253件）の座標が `0,0` です。
> これらは投入せず破棄し、件数を `acquisition_runs` に記録します
> （住所からのジオコーディングは行いません）。東京都の欠損は0.4%のみです。

**診療科目（未取得・任意）**
上記ファイルには標榜診療科が含まれません。同じ制度の別ファイル（診療科目情報）を
取り込めば `facilities.clinic_types` が埋まり、小児歯科・矯正歯科などでの
絞り込みが有効になります。`config/sources.yaml` の `columns.clinic_types` に
実際の列名を追加してください。

**人口メッシュ（取り込み実績あり）**
e-Stat 統計GIS の国勢調査メッシュ統計（`tblTxxxxxxHnn.txt`、Shift-JIS、
ヘッダ直下に日本語のラベル行）。500m・1km どちらでも取り込めます。

> **メッシュ解像度は設定しません。** KEY_CODE の桁数（8桁=1km / 9桁=500m /
> 10桁=250m）から判定し、行ごとに `population_mesh.mesh_size_m` へ保持します。
> API・スコア計算は、投入済みデータから解像度を自動判定します
> （固定値にすると、500mを入れた瞬間に全地点の人口が静かに0になるため）。

人口増減率には2時点が必要です。`--baseline` に前回調査を渡してください。

> 調査回によって同じ概念の列IDが変わります（65歳以上は2020年が `T001141019`、
> 2015年が `T000847016`）。このため基準年ファイルは
> `growth_baseline.columns` に独自の列マッピングを持ちます。

**駅（取り込み実績あり）**
国土数値情報 S12（駅別乗降客数）の zip。全国分をそのまま投入できます。

> 乗降客数は年度ごとに4列（重複コード/データ有無/備考/乗降客数）のブロックで
> 公開されます。ブロックの配置は `passenger_series` で設定し、新しい年度が
> 追加されたら `last_year` を増やすだけで対応できます。
> ファイルに存在しない年度は自動的に読み飛ばし、validate に記録します。
>
> 大規模駅は事業者ごとに複数行で公開されます（新宿駅は11行）。重複コードが
> `1` の行だけが実数を持ち、他は0で公開されるため、駅グループ単位で合算します。
> 合算しないと新宿駅がメトロの入口分（20万人/日）として扱われ、
> アクセススコアが大きく狂います。
>
> S12は都道府県を公開していません。投入済みの人口メッシュから最近傍判定で
> 補完し、範囲外の駅は NULL のままにします（推測で埋めません）。

**行政区域（取り込み実績あり）**
国土数値情報 N03。これを入れるとランキングのエリア名が境界ポリゴンによる
判定になります（未取得の場合は歯科医院の住所から市区町村名を導出し、
`area_label_source` でどちらを使ったか返します）。

> N03 は自治体を「部分」単位で公開します。小笠原村は4,812ポリゴン・23万頂点
> あるため、同一コードの部分をまとめて1自治体1行にします。部分同士は
> 重なり合わないので、ST_Union ではなく ST_Collect で集約します
> （5千島のユニオンは高価で、点包含判定の結果は変わりません）。
>
> コード末尾が `000` の行は自治体ではなく都道府県単位の受け皿です
> （13000「所属未定地」＝埋立地や水面）。これを通すと、実在しない地名で
> メッシュにラベルが付くため除外します。除外件数は validate に記録します。
>
> N03 は `.cpg` で文字コードを UTF-8 と宣言しています（旧レイヤーは
> Shift-JIS）。この宣言を読んで復号します。

### 自動ダウンロード

`config/sources.yaml` に `url` が設定されている情報源（S12・N03）は
自動取得も試せます。歯科診療所と人口メッシュはフォーム経由の配布のため
`url` を空にしてあります（誤ったURLを設定すると、設定漏れが
「サーバ障害」に見えてしまうため）。

```bash
kaigyou-etl run mlit_stations   # url が設定されていれば取得を試みる
kaigyou-etl run-all             # 取得できない情報源があると exit code 2
```

`--offline` を付けると、ネットワークに一切アクセスしません。

### 配布形式が変わったら

列名の変更は `config/sources.yaml` の `columns` に候補を足すだけで対応できます
（コード変更不要）。URL の変更も同ファイルの `url` を書き換えるだけです。
配布形式そのものが変わった場合は、`server/kaigyou_etl/adapters/` に
アダプタを1つ追加し、`adapters/__init__.py` の `ADAPTERS` に登録します。

> **注記:** 4アダプタすべて、実際の配布ファイルで取り込みを検証済みです。
> 別の年度版・別の都道府県を投入する際は、validate ステップの出力
> （検出された列名・件数・除外件数）を確認してください。

## 地価（参考表示）

国土数値情報 L01（地価公示）の標準地を取り込み、候補地点の商圏内について
**用途区分ごとの中央値・レンジ・前年比**と、**最寄りの標準地**を表示します。
地図には「地価」レイヤーとして標準地そのものを点で描きます（面で補間はしません。
地価公示が言っているのは「その標準地の価格」であって、周辺一帯の価格ではないためです）。

**賃料ではありません。** 地価公示は土地1m²あたりの価格（毎年1月1日時点）であり、
建物・階数・契約条件を含みません。要件定義で家賃予測を禁じているため、
ここから賃料を推定する処理は一切入れていません。

### コスト軸（「地価考慮」プロファイル）

`cost_aware` プロファイルでは、地価をコスト軸としてスコアに反映します。
既存の `default` / `pediatric` / `office` は**一切変更していません** —
コスト軸は一つの見方であって、これまでの答えを置き換えるものではないためです。
候補地パネルには両方のスコアが並んで表示されます。

| | 標準 | 地価考慮 | コスト | 地価 |
|---|---:|---:|---:|---:|
| 銀座（中央区） | 47.7 | **36.3** | 0.0 | 1,430万円/m² |
| 三鷹市 | 45.2 | **45.2** | 46.7 | 49万円/m² |

標準モデルでは銀座が上、地価を勘案すると三鷹が上に出ます。
メッシュランキングでも 三鷹市 10位→1位、東久留米市 25位→2位、八王子市 60位→5位と動きます。

仕様:

- **対数スケール**。都内だけで地価は4桁違う（林地 2,240円/m² 〜 銀座 6,710万円/m²）ため、
  線形だと郊外がすべて同じ値に潰れます
- **反転**。安いほど高いスコアになります
- **商圏内に標準地が3地点未満なら算出しません。**
  そして `required_components: [cost]` により、**算出できない地点は総合スコアも出しません**。
  欠測として落として残りの重みで正規化すると「コストが分からない＝コストがかからない」
  という意味になり、実際に最初の実装では**情報の乏しいメッシュが上位1〜4位を占めました**。
  東京都で3地点以上を満たすのは約71%のメッシュです
- 重み（0.20）は他の数値と同じく**仮説**です。`config/scoring.yaml` で変更できます

**それでも賃料ではありません。** 地価はテナント賃料の代理であって、賃料・初期投資額の
予測ではありません。画面でもそう表示しています。

検算: 中央区銀座4丁目2番4 = 67,100,000 円/m²（全国最高地点の公表値と一致）。
用途区分別の中央値は 住宅地 407,000 / 商業地 1,410,000 / 工業地 274,500 円/m²。

## スコアリング

4指標（Demand / Competition / Growth / Accessibility）と総合スコアを算出します。

**重みはコードに埋め込まれていません。** すべて `config/scoring.yaml` にあり、
API はファイルの更新時刻を見て自動で再読み込みします。再起動は不要です。

```yaml
profiles:
  default:
    overall_weights:
      demand: 0.35
      competition: 0.30
      growth: 0.20
      accessibility: 0.15
```

複数のプロファイルを定義でき、リクエスト単位で切り替えられます
（`?profile=pediatric`）。UI のプルダウンにも自動で現れます。

**重みは仮説値です。** 開業実績による較正は行っていないため、
UI では常に「暫定モデル」と表示されます。

### 欠損データの扱い

算出に必要な指標が欠けている場合、**0 とはみなさず「算出不可」として扱います**。

- 部分的に欠けている場合は、残った指標で重みを再正規化
- ただし `min_weight_coverage`（既定 0.5）を下回る場合はスコア自体を出しません
  — 15% の重みしかない1指標だけで「需要スコア」を名乗らせないためです
- 算出できなかった指標は API レスポンスの `unavailable_components` と
  `breakdown[].missing` で明示され、UI にも表示されます

---

### 昼の需要（従業者数）

経済センサスの500mメッシュ「従業者数」を、人口と**別の指標として**需要に入れています。
足し合わせてはいません。通勤者は「職場の近くか自宅の近くか、どちらかで受診する1人」
であって2人ではないためです。合算する代わりに重みを分け、
「昼の1人は夜の1人の何割か」を `config/scoring.yaml` で調整できるようにしています。

```yaml
demand_weights:
  population: 0.28      # 常住人口（夜）
  workers: 0.20         # 従業者数（昼）
```

**従業者数は昼間人口そのものではありません。** 昼間人口には通学者・来街者も含まれますが、
メッシュ単位で公表されているのは従業者数までです。繁華街の来街需要は依然として
捕捉できていません。この区別は `/api/meta` の注意事項にも明記しています。

`office`（オフィス街型）プロファイルは従業者を 0.45 まで引き上げた対照仮説です。
標準プロファイルとの違いを見ると、この指標が順位にどう効くかが分かります。

重みを変えたら、スコアの再計算が必要です。

```bash
kaigyou-etl refresh-stats
kaigyou-etl compute-scores --all-profiles
```

商圏の集計（重い処理）はプロファイルに依存しないため、
1回の集計を全プロファイルで共有します。2つ目以降はほぼ無料です。

### 商圏の形（円 / 徒歩圏）

既定は**円（直線距離）**です。円は川も線路も幹線道路も一跨ぎにするので、
対岸の住民を顧客として数えます。実際に歩いて来られるのは「街路に沿って何m」の
範囲であり、分断のある場所では形が大きく違います。

OpenStreetMap の道路データを投入すると、商圏の形に
**徒歩圏（街路網に沿った距離）** を選べるようになります。

```
円 ─────────  半径500m: 面積 0.78 km²、川の対岸を含む
徒歩圏 ─────  同500m  : 面積 0.29 km²、川で止まる（橋まで迂回すると1.5kmで到達）
```

- 使うのは Geofabrik の道路 shapefile です。PBF 変換も osm2pgrouting も要りません
- 歩ける道路種別は `config/sources.yaml` の `walkable_classes` で指定します。
  自動車専用道（motorway / trunk）は**除外**しています（歩行者通行禁止のため）
- pgRouting が使えない環境、データ未投入、地点の周辺に街路が無い場合は
  **自動的に円に戻り、その旨を表示します**
- どちらの形で算出したかは分析パネルに常時表示されます。
  同じ地点で3倍以上変わるので、形が分からない人口値は解釈できません

**ランキングは円のままです。** 5,449メッシュ分の徒歩圏を毎回計算するのは
別規模のバッチ処理になるためで、地点分析のみの対応です。

**規模と所要時間に注意。** 関東の抽出は数百MBあり、`bbox` で東京都本土に絞っても
エッジ数は数十万〜百万規模になります。`pgr_nodeNetwork` による交差点分割は
この規模で長時間かかり、Supabase 無料枠（500MB）を圧迫する可能性もあります。
**まず 23区だけの狭い bbox で試すことを勧めます**（`config/sources.yaml` の `bbox`）。

```yaml
bbox: [139.56, 35.53, 139.92, 35.82]   # 23区のおおよその範囲
```

**ライセンス:** OpenStreetMap のデータは ODbL です。出典表示は義務であり、
他の情報源と同じく「この画面の数値の出典」に表示されます。

## GIS 処理

空間処理はすべて PostGIS 側にあります（`db/migrations/005_functions.sql`）。

- **商圏**: `ST_Buffer(point::geography, radius)` — 度ではなくメートルの真円
- **商圏人口**: メッシュポリゴンと商圏円の交差面積で按分
  （`ST_Area(ST_Intersection(...)::geography) / ST_Area(mesh::geography)`）
- **競合数**: `ST_DWithin(geography)` — GIST インデックス使用
- **最寄り施設／駅**: geography の KNN 演算子 `<->`
- **人口増減率**: 商圏内メッシュの人口加重平均

メッシュサイズは固定値ではありません。`population_mesh.mesh_size_m` に行ごとに保持し、
メッシュコードの桁数（8桁=1km / 9桁=500m / 10桁=250m）から自動判定します。

## 商圏分析データセット API

`GET /api/dataset?lat=&lng=&radius=` — **1地点について分かることを、ひとつのJSONにまとめて返します。**
画面向けの他のエンドポイントと違い、「この場所について推論する読み手」向けの形です
（別のプログラム、JSONを直接読む人、あるいはLLM）。

```
GET /api/dataset?lat=35.6717&lng=139.7650&radius=1000
```

| パラメータ | 既定 | 意味 |
|---|---|---|
| `lat` / `lng` | 必須 | 地点 |
| `radius` | 1000 | 商圏半径（m, 100〜10000） |
| `catchment` | circle | `circle`（直線距離）/ `walk`（街路網） |
| `profile` | active_profile | スコアのプロファイル。全プロファイルの結果は常に含まれます |
| `max_clinics` | 50 | 列挙する歯科診療所の上限。`0` なら件数のみ |
| `geometry` | false | 商圏ポリゴンを含める |

### 含まれるもの

| セクション | 内容 |
|---|---|
| `location` | 都道府県・市区町村（境界ポリゴンからの判定） |
| `catchment` | 商圏の形・面積・（任意で）ポリゴン |
| `demand.residents` | 半径別の人口・年齢3区分・世帯数・人口増減率 |
| `demand.daytime` | 半径別の従業者数・事業所数 ＋ **産業分類別の内訳** |
| `competition` | 半径別の歯科医院数・人口/歯科・最寄り歯科 ＋ 商圏内の医院一覧 |
| `access` | 最寄り駅 ＋ 商圏内の駅（事業者・路線・乗降客数・距離） |
| `cost` | 地価公示の中央値・用途区分別・最寄りの標準地 |
| `scores` | **全プロファイル**の総合スコアと4〜5成分・重み |
| `relative_position` | **分布の中での位置**（都道府県内・市区町村内のパーセンタイル） |
| `competition.proximity` | **競合の距離の階段**（1/3/5/10/20番目）と密度 |
| `demand.distribution` | **商圏内の人口の散らばり**（最大メッシュのシェア・無人メッシュ数） |
| `regulation` | **用途地域・容積率・建蔽率** |
| `definitions` | **全項目の単位・定義・出典** |
| `data_quality` | 未取得のデータセット・注意事項・既知の弱点 |
| `provenance` | 出典・公表日・ライセンス |

### この形にした理由

**単位と定義を同梱する。** 読み手はこのプロジェクトを知りません。`従業者数` を昼間人口と、
`円/m²` を賃料と読み違えると、自信のある間違った答えが出ます。`definitions` に
「昼間人口ではない」「賃料ではない」と明記してあります。

**欠測とゼロを区別する。** `null` は不明、`0` は数えた結果のゼロです。
データセットごと無い場合は `data_quality.unavailable_datasets` に名前が出ます。
「近くに歯科医院が無い」を、テーブルが空なだけの状態から読み取れないようにするためです。

**注意事項をデータと一緒に運ぶ。** 免責と各データの弱点が同じ文書に入っているので、
これを読んで文章を書く側は、それを持った状態で書けます。

**判断はしません。** 推奨・成功確率・売上予測はこのAPIからは出ません
（テストで文字列レベルで禁止しています）。数値と、その意味だけを返します。

### 「絶対値」ではなく「位置」を返す

読み手が一般的な知識として持っていないのは、絶対値ではなく**分布の中での位置**です。
銀座と三鷹を並べると、その差がそのまま出ます。

| | 銀座 | 三鷹 |
|---|---:|---:|
| 人口（東京都内の位置） | 13,268人（**30パーセンタイル**） | — |
| 歯科医院（同上） | 186件（**100パーセンタイル**） | — |
| 人口/歯科（同上） | **0パーセンタイル**（都内で最も競合過多） | — |
| 20番目に近い歯科まで | **158m** | **1,206m** |
| 歯科の密度 | 59.2件/km² | 3.8件/km² |
| 最大メッシュの人口シェア | 0.31（4メッシュは無人） | 0.14 |
| 用途地域・容積率（最寄標準地） | 商業・800% | 第一種住居・200% |

「銀座は地価が高い」は誰でも知っています。「**住民は都内30パーセンタイルなのに、
競合と地価は100パーセンタイル、半径158mに20軒**」は実データの分布がないと出せません。

市区町村内の尺度も併せて返します（銀座は中央区内では人口3パーセンタイル）。
都内では平凡でも区内では最上位、という場所を取りこぼさないためです。

応答サイズの目安: 銀座・半径1km で約26KB（医院50件込み）、`max_clinics=0` で約16KB。

### 画面から取り出す

地図で地点をクリック → 候補地パネルの **「JSONで出力」** を押すと出力パネルが開きます。

- **JSONをコピー** — クリップボードへ。詰めた形式で出します（整形すると倍近くなり、
  それはそのままLLMのトークンになるため）。クリップボードが使えない環境
  （http接続・権限拒否など）では、黙って失敗せずファイル保存に切り替えます
- **ダウンロード** — `kaigyou-35.67170-139.76500-1000m.json` として保存。
  こちらは人がエディタで開くので整形して出します
- **歯科医院の一覧を含める** — 外すと 26KB → 16KB。件数は外しても残ります

押したあとにバイト数が出るので、貼り付ける前に量が分かります。

| エンドポイント | 内容 |
|---|---|
| `GET /api/candidate-analysis?lat=&lng=&radius=` | 任意地点の商圏分析（中心機能） |
| `GET /api/rankings` | メッシュ単位ランキング |
| `GET /api/compare?points=lat,lng;lat,lng` | 最大3地点の比較 |
| `GET /api/clinics` / `stations` / `meshes` / `municipalities` | GeoJSON レイヤー |
| `GET /api/data-status` | **取得できたデータ／できなかったデータと原因** |
| `GET /api/meta` | スコアリングモデル定義・免責事項 |

すべての分析レスポンスに `provenance`（出典・データ時点・取込日時・サンプル判定）、
`disclaimer`、`score_disclaimer` が含まれます。
